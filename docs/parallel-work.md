# Раздельная работа Codex и Claude

## Релиз 1.0.0: приоритетное правило от 2026-10-25

Единый источник релиза — `C:/Users/User/Desktop/ustal-release-1.0.0`,
ветка `release/ustal-1.0.0`. Точный SHA и manifest указаны в
`docs/RELEASE_BASELINE.md` и `release-baseline.json`. Codex — единственный
интегратор. Claude начинает только с согласованного полного baseline,
передаёт изменения патчем с base SHA/manifest hash. При несовпадении
baseline остановиться, не продолжать в старой рабочей папке.
Старые worktree сохраняются вместе с WIP и не обновляются автоматически.
Разрешения на commit/push/merge/deploy этим правилом не даются.

ссылки на node_modules и не копируйте секреты. Для каждой папки зависимости
устанавливаются отдельно после синхронизации package-lock.json.

## Первое переключение

На момент настройки обе рабочие ветки созданы от
`07d49fe7a4fce32bba4e40862ba81d863b8d1ef4`.
Незакоммиченные заказы, аватар, города и SDK-правки остались в исходной папке.
Их нельзя автоматически считать принадлежащими одному агенту.

1. Завершить изменения исходной папки одним ответственным интегратором:
   проверить diff, зависимости, тесты и разложить согласованные изменения на
   коммиты. Не выполнять это автоматически только ради настройки worktree.
2. После интеграции обновить каждую чистую рабочую ветку командой
   `git merge --ff-only main` из её собственной папки. Если ветка уже разошлась,
   использовать обычный merge и проверить конфликты; без reset/rebase/force push.
3. Открыть ustal-codex как проект Codex, ustal-claude как проект Claude Code
   либо переключить корень файлового моста Claude. Существующий чат и мост
   автоматически не переключаются. Проверить путь перед каждой записью.

## Каждая задача

- Работать в своей папке; коммитить только файлы своей задачи после проверок.
- Сложные задачи удобно вести в отдельной ветке от актуального main.
- До согласованного коммита не добавлять чужие правки, .env, .ai-bridge или
  локальные handoff-материалы в индекс. Не делать `git add .` вслепую.
- Передавать интегратору SHA, список файлов, проверки, миграции/seed и ограничения.
- Общие API-контракты согласовывать заранее. Раздельные папки предотвращают
  перезапись файлов, но не логические конфликты.

## Релиз

Любой агент может быть интегратором, но одновременно только один.

1. Получить разрешение на релиз. Зафиксировать в handoff владельца релиза,
   текущий production SHA, целевую ветку/SHA и проверки. Если другой агент
   уже выполняет релиз, дождаться окончания; не перехватывать его.
2. В чистом main объединить только готовые ветки обычным merge. Проверить
   объединённый код, а не только ветку автора. Незакоммиченные изменения
   исходной папки сначала разобрать; не переключать её принудительно.
3. Обычный push, только с разрешением. После публикации сверить SHA remote.
4. Перед деплоем убедиться, что текущая production-версия является предком
   выбранного коммита (`git merge-base --is-ancestor OLD_SHA TARGET_SHA`).
   Если нет — остановиться и согласовать расхождение, не откатывать чужую работу.
5. Обновить сервер до проверенного SHA. Учитывать, что deploy-app.sh выполняет
   git pull: если main успел измениться, сначала проверить новый состав релиза.
   Вести запись SHA фактически запущенного кода, а не только локального HEAD.
6. Выполнить необходимые миграции/seed, health-check и проверки функций.
   Мобильный Expo-клиент обновляется отдельно от API.
7. Записать результат и освободить роль интегратора. Обновить обе рабочие ветки
   через merge. Никогда не выкладывать старую изолированную ветку напрямую.

Это организационный порядок, а не автоматическая серверная блокировка.
Настройка worktree не меняет CI, сервер и доступы и не запускает деплой.

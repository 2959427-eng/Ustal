# USTAL — Архитектура MVP

## 1. Обзор

USTAL — мобильная AI-платформа услуг и поручений без ролей (заказчик/исполнитель определяются действием), без комиссии, без гео (только город), с ядром в виде AI-профиля возможностей и AI-matching.

Монорепозиторий:

```
ustal/
  apps/
    mobile/   — Expo (React Native) приложение, единственный пользовательский клиент
    api/      — REST API, Node.js modular monolith
    worker/   — фоновые задачи: AI-вызовы, matching, уведомления
    admin/    — Next.js веб-админка (для сотрудников, не для пользователей)
  packages/
    domain/       — доменные типы и бизнес-правила, общие для api/worker
    database/      — схема БД, миграции, клиент
    validation/    — Zod-схемы запросов/ответов и AI JSON Schema
    api-client/    — типизированный клиент API для mobile и admin
    ai/            — провайдеры STT / extraction / embeddings / moderation
    matching/       — retrieval + scoring
    ontology/       — работа с онтологией и синонимами
    config/         — рантайм-конфигурация (пороги, лимиты, модели) без деплоя
    queue/          — pg-boss поверх Postgres, общий для api (ставит задачи) и worker (забирает)
    storage/        — провайдеры хранения медиа (local для разработки, s3 — Timeweb Cloud), см. добавление #10
  tests/
  docs/
  infrastructure/docker/
  docker-compose.yml
  .env.example
```

Правило: `api` и `worker` не дублируют бизнес-логику — обе используют `packages/domain`, `packages/matching`, `packages/ai`, `packages/ontology`. `worker` — единственное место, где выполняются AI-вызовы и подбор кандидатов; `api` только ставит задачи в очередь и отдаёт уже посчитанные результаты (кроме синхронных быстрых операций, см. ниже).

## 2. Технологический стек (с решениями по открытым пунктам ТЗ)

### Mobile
Expo + Expo Router + TypeScript + TanStack Query + React Hook Form + Zod + SecureStore + Expo Notifications + expo-av (запись голоса) + expo-image-picker + Linking (`tel:`, `whatsapp://`) + deep links из push.

### Backend API
Node.js + TypeScript, Fastify (лёгкий, быстрый, хорошая OpenAPI-генерация через `@fastify/swagger`) как HTTP-фреймворк modular monolith. REST, OpenAPI 3.1.

### БД и ORM — решение
ТЗ оставляет выбор «Prisma или Drizzle» открытым. **Выбираем Drizzle ORM + drizzle-kit** (SQL-миграции), потому что:
- нативная поддержка типа `vector` (pgvector) без плагинов и raw SQL обвязки;
- миграции — обычный SQL, что требует ТЗ явно («SQL-миграции»);
- легче для worker'а писать сырые SQL-запросы для scoring/retrieval, где нужен полный контроль над `<=>`/`<->` операторами pgvector.

### Очередь задач — решение
ТЗ требует «простую очередь на PostgreSQL» без Redis/BullMQ, но не называет библиотеку. **Выбираем `pg-boss`** (работает поверх обычной PostgreSQL, `SKIP LOCKED`, ретраи, cron, не требует Redis) для типов задач: `profile_extraction`, `order_extraction`, `moderation`, `embedding`, `matching_run`, `notification_dispatch`. Таблица `background_jobs` в ТЗ соответствует внутренним таблицам pg-boss + собственному тонкому слою логирования поверх (для audit).

### Админка
Next.js (App Router) + TypeScript, серверная авторизация администратора (отдельная таблица `admin_users`, не путать с `users`), защищена отдельным паролем/сессией, не имеет отношения к мобильной авторизации.

### AI-провайдеры
Интерфейсы `SpeechToTextProvider`, `StructuredExtractionProvider`, `EmbeddingProvider`, `ModerationProvider` в `packages/ai`. Конкретные реализации подключаются через `packages/config` (имя провайдера и модель — из конфигурации, без релиза). По умолчанию — экономные модели (Haiku/GPT-4o-mini/Gemini Flash уровня) для extraction; правило-based moderation для дешёвых случаев, AI-moderation — только для пограничных. Локальная разработка — `MockAIProvider` для всех четырёх интерфейсов (детерминированные фикстуры, без сетевых вызовов).

## 3. Деплой (по вашей схеме)

Ваша схема верна для backend-части, уточняю роли и добавляю недостающий кусок — мобильную сборку, которая по определению не «хостится»:

```
GitHub (монорепозиторий ustal/)
   │  git push → GitHub Actions (CI/CD)
   │    ├── lint / typecheck / unit / integration tests
   │    ├── build Docker images: api, worker, admin
   │    └── docker push → registry
   ▼
Timeweb Cloud — App Platform (Cloud Apps)
   ├── api      (деплой из Dockerfile, REST, порт наружу через HTTPS)
   ├── worker   (деплой из Dockerfile, без внешнего порта, читает pg-boss очередь)
   └── admin    (деплой из Dockerfile, отдельный поддомен, доступ только для сотрудников)
   │  запросы к БД по приватной сети / DSN из секретов App Platform
   ▼
PostgreSQL — self-hosted на облачном сервере Timeweb Cloud, с расширением
   pgvector, установленным вручную (apt-пакет postgresql-16-pgvector, как и
   в этой сессии при локальной проверке). Managed PostgreSQL от Timeweb Cloud
   рассматривается как альтернатива, если у него подтвердится поддержка
   произвольных расширений (pgvector в списке разрешённых официально не
   значится на момент написания — проверить в поддержке перед переключением).
   + Object Storage (S3-совместимое хранилище Timeweb Cloud, для фото заказов
     и, опционально, аудиозаписей) — в исходной схеме отсутствовало, добавляю:
     без него негде хранить order_media и voice-вложения.

Мобильное приложение — ОТДЕЛЬНЫЙ канал, не хостинг:
   GitHub → EAS Build (Expo Application Services)
     ├── Android: собирает .aab/.apk, может публиковать в Play Console
     └── iOS: собирает .ipa, требует Apple Developer аккаунт (см. открытые вопросы)
   Push-уведомления идут через Expo Push API → APNs (iOS) / FCM (Android),
   backend лишь вызывает Expo Push API (provider abstraction в packages/ai или
   отдельный packages/notifications).
```

Timeweb Cloud App Platform умеет собирать и автодеплоить приложение прямо из
Dockerfile или docker-compose.yml по git push (в т.ч. по подключённому GitHub-
репозиторию, без отдельного шага docker push в сторонний registry) — это
упрощает пайплайн CI/CD относительно первоначальной трёхступенчатой схемы:
можно оставить lint/typecheck/test в GitHub Actions как гейт для PR, а сборку
образов и раскладку по контейнерам доверить самой App Platform.

## 4. Границы MVP (география, деньги, роли)
Только RU, только выбор города (без гео/карт/PostGIS), цены в копейках/RUB, время в UTC + отображение по таймзоне города, единый тип аккаунта, без комиссии — ranking и matching не содержат платёжных полей.

## 5. Найденные противоречия и неточности ТЗ — с минимальными решениями

Ниже — то, что нашлось при вычитке. По каждому пункту: в чём неточность и какое минимальное решение принято (без остановки всего проекта), как и требует сам документ («При противоречии останови соответствующую часть и опиши минимальное решение»).

1. **Нумерация разделов сбита начиная с раздела 13–14.** Разделы 14, 16, 18, 21, 28, 34, 37 встречаются в тексте дважды с разным содержанием (похоже на артефакт копипаста при финальной сборке промпта). Решение: содержание читалось семантически по заголовкам, а не по номерам; в документации проекта разделы пронумерованы заново по смыслу.
2. **ORM не выбран** («Prisma или Drizzle»). Решение: Drizzle — обоснование в разделе 2.
3. **Библиотека очереди на Postgres не названа.** Решение: pg-boss — обоснование в разделе 2.
4. **Object Storage отсутствует в списке сущностей и в вашей схеме деплоя**, при этом `order_media` и голосовые вложения требуют файлового хранилища. Решение: добавлено явно (Yandex Object Storage либо Supabase Storage — см. раздел 3).
5. **WhatsApp-контакт пользователя не описан как отдельное поле данных**, хотя раздел 18 говорит «написать вотсап (если указал в профиле для связи)». Решение: добавляется `user_profiles.whatsapp_phone nullable` (может отличаться от основного номера).
6. **Скрытие числа выбранных исполнителей — требует уточнения объёма.** Буквально нельзя одновременно (а) дать заказчику список выбранных исполнителей для отметки «выполнено/не выполнено» по каждому и (б) полностью скрыть от него сам факт количества — он неизбежно видит список, значит и количество. Решение: правило трактуется как «не показывать число выбранных исполнителей **кандидатам/исполнителям** в ленте, в карточке заказа и в статусе своего отклика» — именно от них скрывается конкуренция. Заказчику в приватном экране «Выбранные исполнители» список показывается естественным образом (это его рабочий инструмент), но нигде не выводится агрегированная метка вида «Выбрано: 3».
7. **Регулируемые задачи и верификация.** В MVP нет OTP и нет проверки документов — то есть по определению ни один пользователь не может быть «подтверждённым» (raздел 24: «До появления полноценной проверки документов такие заказы направляются на ручную модерацию либо не публикуются автоматически»). Явное следствие, которое ТЗ не проговаривает прямо: в MVP регулируемые заказы **всегда** идут в `manual_review` и никогда не становятся `probable`/`new_opportunity` ни для кого — это не баг, а корректное поведение при отсутствии верификации. Зафиксировано как поведение по умолчанию.
8. **`contact_unlock` не имеет лимита** («Не устанавливай лимит… в MVP»), при этом весь остальной документ последовательно защищается от злоупотреблений (rate limiting на AI-правки, идемпотентность). Решение: не вводим лимит по продуктовой логике (как требует ТЗ), но добавляем **техническую** anti-abuse защиту (rate limit на создание contact_unlock, например не более N в час на пользователя), которая не видна пользователю как ограничение продукта и не требует изменений при появлении будущей монетизации.
9. **iOS push и iOS-сборка зависят от одного и того же внешнего фактора** — Apple Developer аккаунта. ТЗ уже требует не имитировать подписанную сборку без реальных credentials (раздел 34) — то же ограничение автоматически распространяется и на боевые APNs push-уведомления. Зафиксировано как единая открытая зависимость, не две разных.
10. **Найдено при реализации Фазы 2 (AI-профиль):** решение «добавить Object Storage» из п.4 фиксировало инфраструктуру, но исходная модель данных (data-model.md) не содержала ни таблицы учёта загруженных файлов, ни хранилища для эмбеддинга профиля, ни места для `Idempotency-Key`, который тот же документ требует от `POST /profile/inputs`/`POST /orders`. Три минимальных добавления, сделанные в БД без остановки фазы:
    - `media` — таблица учёта фото/аудио (владелец, тип, ключ во внешнем хранилище, mime, размер); `order_media.media_id` и `profile_source_inputs.audio_media_id` ссылались в никуда без неё. Доступ к самому файлу — через новый `packages/storage` (тот же паттерн provider-абстракции, что и `packages/ai`): `local` — диск процесса `api`, для разработки; `s3` — Timeweb Cloud Object Storage, заготовка на боевые credentials (как `openAiProviders` в Фазе 1).
    - `idempotency_keys` — общая таблица (user_id + endpoint + key уникальны), переиспользуемая любым endpoint'ом с идемпотентностью, а не отдельная логика на каждый.
    - `profile_embeddings` — таблица 1:1 с версией `capability_profiles`, по образцу уже существовавшей `order_embeddings`: без неё semantic similarity (matching.md §13.2) не могла бы работать для профиля, только для заказа.

11. **Найдено при реализации Фазы 3 (Заказы):** три небольших уточнения, каждое — минимальное расширение уже существующего дизайна, а не новая сущность:
    - `orders.source_text` стал nullable — для голосового заказа текста ещё нет в момент INSERT (транскрипция приходит асинхронно от worker'а), тот же паттерн, что и `profile_source_inputs.transcript` в Фазе 2. Голосовой заказ хранит вложение как `order_media` с `media.kind='audio'` (`position=-1`), без отдельной колонки `audio_media_id` на `orders` — переиспользует то, что уже есть.
    - Машина состояний заказа (`packages/domain/order.ts`) расширена: `processing`/`moderation_hold` теперь допускают переход в `cancelled`. Без этого автор, чей заказ завис на ручной модерации или ещё обрабатывается AI, не мог бы отменить его сам — блокирующий UX-тупик, который ТЗ не подразумевало.
    - `POST /orders/{id}/publish`: api.md формулировал условие как «`moderation_status = allow`» буквально; трактуется как «`allow` или `allow_with_warning`» — иначе у статуса `allow_with_warning` не было бы смысла (предупреждение показывается автору, а не блокирует публикацию, в отличие от `manual_review`/`reject`).

12. **Найдено при реализации Фазы 4 (Matching):** `minimumRelevanceScore` был выставлен в Фазе 0 «на глаз» (35), без проверки против реальной формулы весов из §13.3. Максимум ОДНОГО сильного сигнала при текущих весах: explicit capability match — 30 баллов, inferred/resource match — 15, semantic similarity — до 15; итог 100 достижим только если сработали одновременно все компоненты, что нереалистично даже для сильного совпадения. Порог 35 отсекал бы вообще всё — включая безупречное точное совпадение способности без других сигналов. Пересчитан на 10 (packages/config/src/runtime-config.ts) — пропускает любой один настоящий структурный сигнал, отсекает кандидатов с нулевыми компонентами по всем осям. Значение по-прежнему меняется без деплоя (см. философию `packages/config`), это не окончательное число, а откалиброванная отправная точка. Заодно найден и исправлен реальный баг: mock-провайдер эмбеддингов возвращал нулевые векторы, а `pgvector`-косинусное расстояние между двумя нулевыми векторами — `NaN`, что отравляло весь score; исправлено (детерминированный ненулевой мок-вектор + defensive `Number.isFinite` в `computeScore` и в worker'е).

13. **Найдено при реализации Фазы 4 (Matching):** `drizzle-orm`'s `sql` tagged template разворачивает обычный JS-массив, переданный как параметр (`${array}`), в кортеж плейсхолдеров через запятую (`$1,$2,$3`, рассчитано на списки `VALUES (...)`), а не в Postgres array literal — поэтому `col = ANY(${array})` падает с ошибкой `op ANY/ALL (array) requires array on right side`. Обнаружено при первом запуске `scripts/verify-phase4.ts` на реальной БД (сразу в двух местах `matching-run.ts` — similarity-запрос и запрос истории завершённых заказов). Решение: локальный хелпер `uuidArrayLiteral(ids: string[])`, явно строящий `ARRAY[$1::uuid,$2::uuid,...]` через `sql.join`; использовать его для любого будущего `= ANY(${...})` с массивом параметров в сыром SQL (не проблема для `drizzle-orm`'s `inArray()` — она генерирует корректный SQL сама, баг только в сыром `sql\`...\`` шаблоне).
14. **Найдено при реализации Фазы 4 (Matching):** проверочные скрипты (`scripts/verify-phaseN.ts`) переиспользовали одни и те же seed-города при каждом запуске и не откатывали прикладные данные между прогонами (`boss.clearStorage()` чистит только очередь pg-boss, не таблицы приложения) — при повторном запуске `verify-phase4.ts` matching city-scoped SQL находил кандидатов, зарегистрированных в предыдущих прогонах того же скрипта, и точная проверка «ровно 1 кандидат» стала нестабильной (зависела от истории запусков БД). Это баг тестового скрипта, а не matching-кода — в проде city-scoped выборка ВСЕХ активных пользователей города корректна и обязательна. Решение: `verify-phase4.ts` создаёт для каждого прогона два новых города напрямую в БД (уникальное имя с timestamp+random) вместо переиспользования seed-городов — изолирует прогон без truncate чего-либо в БД.

15. **Найдено при реализации Фазы 5 (Отклики и обсуждение):** `drizzle-orm`'s postgres-js driver оборачивает реальную ошибку Postgres в `DrizzleQueryError`, и код ошибки (`23505` — unique violation, используется в `POST /orders/{id}/responses` для превращения дубликата активного отклика в 409 вместо 500) лежит не на самой брошенной ошибке, а на `err.cause.code` (см. `node_modules/drizzle-orm/errors.ts`). Обнаружено сквозным сценарием (`scripts/verify-phase5.ts`, шаг 5) — первая попытка проверять `err.code` напрямую пропускала обработку и роняла запрос в 500. Исправлено; тот же паттерн (`err.cause?.code`) — правильный способ ловить конкретные Postgres error code из любого сырого insert/update через drizzle, а не только здесь.
16. **Найдено при реализации Фазы 5:** технический anti-abuse rate limit на `POST /orders/{id}/contact-unlocks` (`CONTACT_UNLOCKS_PER_HOUR`, architecture.md §5 п.8) — per-user лимит, независимый и не связанный с общим `@fastify/rate-limit` (100 запросов/минуту на IP, apps/api/src/app.ts, защита от злоупотребления API в целом). В сквозном тесте (`scripts/verify-phase5.ts`, шаг 16) добор до настоящего значения по умолчанию (30) потребовал бы ~90 HTTP-запросов подряд и упёрся бы в общий IP-лимит раньше, чем в проверяемый бизнес-лимит — два независимых защитных механизма, рассчитанных на разные объёмы трафика, не должны маскировать друг друга в тесте. Решение: тестовый скрипт временно понижает `CONTACT_UNLOCKS_PER_HOUR` через `process.env` перед первым вызовом `loadEnv()` (до `buildApp()`) — сам механизм и код проверяются полностью, только с калиброванным для теста, а не боевым числом.
17. **Найдено при реализации Фазы 5:** `device_installations` (docs/data-model.md) не имела уникального индекса, при этом api.md требует «идемпотентность по `expo_push_token` при повторной регистрации устройства (upsert, не дубли)» — без уникального ограничения `onConflictDoUpdate` не на что опереться. Добавлена уникальность самого `expo_push_token` (не пары user_id+token) — тот же токен, переехавший на другой аккаунт (переустановка приложения на другом аккаунте на том же устройстве), переписывает владельца, а не заводит вторую строку; миграция `0003_cuddly_preak.sql`.

18. **Найдено при реализации Фазы 6 (Договорённость и закрытие):** план фаз перечислял «блокировка новых откликов» отдельным пунктом от «Договорились» (первое назначение исполнителя) — не очевидно само по себе, блокируется ли приём новых откликов уже в момент первого назначения (заказ переходит `published` → `negotiating`) или только при явном закрытии заказа. Учитывая соседний пункт «множественные assignments без счётчиков» — продукт явно допускает, что автор продолжает выбирать исполнителей по мере поступления новых откликов уже после первого выбора (иначе для многоисполнительских заказов пришлось бы иметь все отклики заранее, до первого назначения, что не соответствует естественному сценарию). Решение: `negotiating` сам по себе не блокирует `POST /orders/{id}/responses` — только статус `closed` после явного `POST /orders/{id}/close`. Заказ в статусе `negotiating` перестаёт быть виден в `/feed` (там фильтр `status = 'published'`), но уже осведомлённый о заказе пользователь может откликнуться напрямую по ID вплоть до закрытия — так же, как автор заказа получает уведомление о новом отклике вне зависимости от источника.

19. **Найдено при реализации Фазы 7 (Результат работы и отзывы):** api.md для `POST /orders/{id}/assignments/{assignmentId}/not-completed` явно требует «опциональную причину», но `order_assignments` (docs/data-model.md) не содержала для неё поля. Минимальное решение — добавлено `order_assignments.not_completed_reason` (nullable text, миграция `0004_same_rumiko_fujikawa.sql`), заполняется только веткой not-completed, для `completed` остаётся `null`. Тот же паттерн, что и в добавлениях #10/#11/#17: если api.md явно описывает поле ввода, а модель данных места для него не предусматривает — это гэп модели, а не то, что можно молча отбросить.

20. **Найдено при реализации Фазы 8 (Админка и модерация):** `POST /auth/refresh` до этой фазы не проверял `users.status` вообще — заблокированный администратором аккаунт мог продолжать получать новые access token'ы через уже выданный refresh, пока сам refresh не истечёт (до `REFRESH_TOKEN_TTL_DAYS`, а не до ближайшего логина/действия). Обнаружено не тестом, а при проектировании функции блокировки в админке — блокировка `users.status='blocked'` без этой проверки была бы косметической (пользователь продолжал бы работать с уже выданной парой токенов). Access token (JWT, `ACCESS_TOKEN_TTL_MINUTES`) отзыву не подлежит в принципе — общее для MVP ограничение (нет denylist'а для access token, только для refresh-сессий), задокументировано как принятый компромисс, а не гэп. Решение: `/auth/refresh` теперь читает `users.status`, и при `status !== 'active'` — отзывает саму сессию (`user_sessions.revoked_at`) и возвращает 401, а не просто отказывает в этот раз (иначе следующий refresh с тем же токеном снова дошёл бы до проверки статуса — незачем держать валидный, но обречённый refresh живым). Проверено `scripts/verify-phase8.ts`, шаг 6-7.

21. **Найдено при реализации Фазы 8 (сборка `apps/admin`):** workspace-пакеты (`packages/config`, `packages/database`, ...) пишут внутренние relative-импорты в NodeNext-стиле с явным `.js` (`export * from "./env.js"`, хотя физически файл `env.ts`) — того требует `moduleResolution: "NodeNext"` в `tsconfig.base.json`, и так их корректно резолвит `tsx`/Node ESM-загрузчик у `apps/api`/`apps/worker`. Next.js 14's webpack-бандлер этот же `.js`-суффикс за пределами `moduleResolution: "NodeNext"`-контекста не резолвит в `.ts`/`.tsx` во всех случаях компиляции — конкретно ломалось при затягивании `@ustal/config` в граф Server Actions ("flight"-компиляция через `next-flight-action-entry-loader`), с ошибкой `Module not found`. Переписать импорты самих пакетов нельзя — тот же код используется `tsx`, которому явный `.js` обязателен. Решение: `apps/admin/next.config.mjs` → `webpack: (config) => { config.resolve.extensionAlias = { ".js": [".ts", ".tsx", ".js"] }; return config; }` — учит webpack тому же правилу, что уже действует для tsx/Node ESM, не трогая исходники пакетов. Отдельно (независимая, но похожая по природе находка) — собственные relative-импорты `apps/admin`'а тоже писались с `.js`-суффиксом по унаследованной привычке; для файлов, целиком принадлежащих `apps/admin` (не общих с tsx-рантаймом), суффикс просто убран — webpack резолвит extension-less relative-импорты нативно без дополнительной настройки. Проверено полной сборкой (`npm run build -w @ustal/admin`, все 9 роутов) и `scripts/verify-admin-e2e.mjs` (headless Chromium против собранного production-сервера).

22. **Уточнение архитектуры (не гэп, а решение, зафиксированное явно):** `apps/admin` с самого начала (Фаза 1, `package.json` уже зависел от `@ustal/database`/`@ustal/domain`, а не от `@ustal/api-client`) спроектирован обращаться **напрямую к Postgres через `@ustal/database`** из Server Components/Server Actions — минуя Fastify REST API (`apps/api`) целиком. Никакого `/admin/*` REST-контракта нет и не планируется: страницы читают из БД в Server Component, мутации идут через Server Actions с прямыми `db.insert`/`db.update`. `apps/api/src/app.ts` содержит явный комментарий об этом на случай, если это не будет очевидно из отсутствия `apps/admin` → `@ustal/api-client` в графе зависимостей. Причина: у админки нет мобильного/публичного клиента, которому нужен был бы стабильный versioned REST-контракт — она сама себе и сервер, и единственный клиент, а прямой доступ к БД в Server Components — идиоматичный паттерн Next.js App Router.

23. **Найдено при реализации Фазы 8 (headless-браузер vs REST для E2E):** логин админки (`apps/admin/app/login/page.tsx`) — `"use client"`-компонент на `useFormState`/`useFormStatus`, поэтому реальная отправка формы идёт через React Server Actions "flight"-протокол (заголовок `Next-Action` + специально закодированное тело, привязанное к build-специфичному хэшу действия), а не обычный `<form method="post">`, который можно было бы просто повторить через `curl`. `scripts/verify-phaseN.ts` (Fastify `app.inject()`) для админки в принципе неприменим — это не REST API. Решение: отдельный `scripts/verify-admin-e2e.mjs`, headless Chromium через `playwright-core` (без полного пакета `playwright` — браузерный бинарник уже присутствует в окружении по пути `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, качать через `playwright install` не нужно и в некоторых окружениях невозможно из-за egress-ограничений). Дополнительная деталь окружения: этот конкретный `chrome`-бинарник (Chromium 1194) не поддерживает legacy `--headless=old`, который `playwright-core` 1.48 подставляет по умолчанию при `headless: true` — потребовалось явно передать `args: ["--headless=new"]` поверх (Chrome берёт последнее указанное значение флага). Сценарий проверяет полный цикл: неавторизованный доступ → редирект на `/login`; неверный пароль → остаётся на `/login` с общей ошибкой (не палит, что именно неверно — тот же принцип, что и в `/auth/login`); верный логин → httpOnly cookie-сессия → дашборд; все 7 защищённых страниц рендерятся; мутирующее действие (блокировка/разблокировка пользователя через Server Action) реально меняет `users.status` в БД, а не только рендерится; logout очищает cookie.

24. **Найдено при подключении боевого OpenAI-ключа (после Фазы 8):** `packages/ai/src/providers/openai.ts` и `packages/storage/src/providers/s3.ts` были заготовками ещё с Фазы 1-2 — каждый метод буквально бросал `notImplemented()`. Это оставалось незамеченным весь проект, потому что все 8 фаз проверялись через `AI_PROVIDER=mock`/`MEDIA_STORAGE_PROVIDER=local` (осознанный выбор для песочницы без боевых credentials, см. раздел 3) — реальный провайдер не вызывался ни разу до этого момента. Как только пользователь подключил настоящий `OPENAI_API_KEY`, любой AI-вызов немедленно упал бы с `not implemented`. Реализовано:
    - **`openAiStt`/`openAiExtraction`/`openAiEmbedding`/`openAiModeration`** — реальные вызовы `whisper-1` / `gpt-4o-mini` (Structured Outputs через `response_format: json_schema`) / `text-embedding-3-small`. JSON-схема для Structured Outputs строится из уже существующих Zod-схем (`capabilityExtractionResultSchema`/`orderExtractionResultSchema`, плюс новая `moderationDecisionSchema` в `packages/validation/src/orders.ts` — контракта для AI-модерации раньше не существовало вовсе) через `zod-to-json-schema`, а не переписывается вручную — единый источник истины для JSON-схемы вызова и рантайм-валидации ответа.
    - **Сознательно без `strict: true`** в Structured Outputs: strict-режим OpenAI требует `additionalProperties: false` на каждом object-узле схемы и не поддерживает произвольные словари, а `capabilityExtractionResultSchema.resources[].attributes` — это `z.record()` (нужен для `user_resources.attributes jsonb`, который принципиально принимает произвольные ключи). Без реального ключа в песочнице поведение strict-режима на такой схеме проверить нельзя — решение консервативное: обычный (non-strict) `json_schema` + `zodSchema.parse()` как единственная фактическая граница валидации ответа модели (тот же принцип, что и раньше: LLM не пишет в БД напрямую без прохождения этой проверки).
    - **`moderateWithRules`** (жёсткие правила по ключевым словам) остался как был — AI вызывается только для пограничных случаев, как и требует раздел 12 ТЗ; добавлена защита `regulated=true` → decision пересчитывается в `manual_review`, если модель вопреки системному промпту всё же вернула `allow`/`allow_with_warning` (инвариант раздела 7 не должен зависеть от точности следования промпту).
    - **`createS3Storage`** (Timeweb Cloud Object Storage) — `@aws-sdk/client-s3` с `forcePathStyle: true` (нужно почти всем не-AWS S3-совместимым провайдерам). Единственное изменение публичного контракта: `MediaStorageProvider.resolvePath()` стал `async` (`Promise<string>`, было `string`) — для local это осталось тривиальным построением пути, для s3 возвращает presigned GET URL через `@aws-sdk/s3-request-presigner` (15 минут по умолчанию), а не физический путь на диске. Оба вызывающих места (`apps/worker/src/handlers/{profile,order}-extraction.ts`) уже были внутри async-функций — просто добавлен `await`. `openAiStt.transcribe` теперь читает audio-вход и как обычный файловый путь, и как `http(s)://` URL — один код работает для обоих storage-провайдеров без ветвления на стороне вызывающего.
    - `getAiProviders()`/`getMediaStorage()` при недостающем `OPENAI_API_KEY`/`OBJECT_STORAGE_*` бросают явную ошибку с точным списком отсутствующих переменных при первом реальном вызове (не раньше — сами объекты-бандлы строятся лениво), а не откладывают падение до середины запроса без объяснения.
    - Проверено: typecheck/lint/test по всем 15 workspace-пакетам чисто, новые юнит-тесты (`packages/ai/src/providers/openai.test.ts`, `packages/storage/src/index.test.ts`) на то, что можно проверить без сетевого вызова к реальному API (сборка клиента, явные ошибки при отсутствии ключа/credentials, `moderateWithRules` без ключа вовсе), полная регрессия `verify-phase2.ts`…`verify-phase8.ts` на `AI_PROVIDER=mock` всё ещё зелёная. **Реальные Structured Outputs/Whisper/embeddings/S3-запросы против боевого API не проверялись в этой сессии** — в песочнице нет реального ключа; это первое, что стоит прогнать вручную после подключения (см. AI_HANDOFF.md).

25. **Подготовлен Timeweb Cloud EU relay для OpenAI без смены провайдера хостинга:** основной USTAL остаётся на Timeweb Cloud, а отдельный маленький VPS в том же кабинете Timeweb создаётся в локации Frankfurt или Amsterdam и поднимает Caddy reverse proxy из `infra/timeweb/relay`. Приложение теперь поддерживает `OPENAI_BASE_URL` в `packages/config` и передаёт его в OpenAI SDK (`packages/ai/src/providers/openai.ts`), поэтому `api`/`worker` могут ходить на `https://ai-relay.<domain>/v1`. Основной app-сервер хранит не настоящий OpenAI-ключ, а `RELAY_CLIENT_TOKEN` в переменной `OPENAI_API_KEY`; relay пускает `/v1/*` только с этим bearer-токеном и заменяет `Authorization` на настоящий `OPENAI_API_KEY`, который хранится только на relay-сервере. Для основного VPS добавлен `infra/timeweb/app` — prod compose с `api`/`worker`/`admin`/Postgres/pgvector за Caddy. Пошаговая инструкция по DNS, `.env`, запуску и проверкам зафиксирована в `docs/timeweb-deploy.md`. В песочнице проверены env-контракт и unit-тесты без реального OpenAI-ключа; реальный e2e вызов через relay требует вашего ключа и созданного VPS.

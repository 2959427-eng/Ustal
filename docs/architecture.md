# USTAL — Архитектура MVP

## 1. Обзор

USTAL — мобильная AI-платформа услуг и поручений без ролей (заказчик/исполнитель определяются действием), без комиссии, без гео (только город), с ядром в виде AI-профиля возможностей и AI-matching.

Монорепозиторий:

```
ustal/
  apps/
    mobile/   — Expo (React Native) приложение, единственный пользовательский клиент
    api/      — REST API, Node.js modular monolith
    worker/   — фоновые задачи: AI-вызовы, matching, уведомления
    admin/    — Next.js веб-админка (для сотрудников, не для пользователей)
  packages/
    domain/       — доменные типы и бизнес-правила, общие для api/worker
    database/      — схема БД, миграции, клиент
    validation/    — Zod-схемы запросов/ответов и AI JSON Schema
    api-client/    — типизированный клиент API для mobile и admin
    ai/            — провайдеры STT / extraction / embeddings / moderation
    matching/       — retrieval + scoring
    ontology/       — работа с онтологией и синонимами
    config/         — рантайм-конфигурация (пороги, лимиты, модели) без деплоя
    queue/          — pg-boss поверх Postgres, общий для api (ставит задачи) и worker (забирает)
    storage/        — провайдеры хранения медиа (local для разработки, s3 — Timeweb Cloud), см. добавление #10
  tests/
  docs/
  infrastructure/docker/
  docker-compose.yml
  .env.example
```

Правило: `api` и `worker` не дублируют бизнес-логику — обе используют `packages/domain`, `packages/matching`, `packages/ai`, `packages/ontology`. `worker` — единственное место, где выполняются AI-вызовы и подбор кандидатов; `api` только ставит задачи в очередь и отдаёт уже посчитанные результаты (кроме синхронных быстрых операций, см. ниже).

## 2. Технологический стек (с решениями по открытым пунктам ТЗ)

### Mobile
Expo + Expo Router + TypeScript + TanStack Query + React Hook Form + Zod + SecureStore + Expo Notifications + expo-av (запись голоса) + expo-image-picker + Linking (`tel:`, `whatsapp://`) + deep links из push.

### Backend API
Node.js + TypeScript, Fastify (лёгкий, быстрый, хорошая OpenAPI-генерация через `@fastify/swagger`) как HTTP-фреймворк modular monolith. REST, OpenAPI 3.1.

### БД и ORM — решение
ТЗ оставляет выбор «Prisma или Drizzle» открытым. **Выбираем Drizzle ORM + drizzle-kit** (SQL-миграции), потому что:
- нативная поддержка типа `vector` (pgvector) без плагинов и raw SQL обвязки;
- миграции — обычный SQL, что требует ТЗ явно («SQL-миграции»);
- легче для worker'а писать сырые SQL-запросы для scoring/retrieval, где нужен полный контроль над `<=>`/`<->` операторами pgvector.

### Очередь задач — решение
ТЗ требует «простую очередь на PostgreSQL» без Redis/BullMQ, но не называет библиотеку. **Выбираем `pg-boss`** (работает поверх обычной PostgreSQL, `SKIP LOCKED`, ретраи, cron, не требует Redis) для типов задач: `profile_extraction`, `order_extraction`, `moderation`, `embedding`, `matching_run`, `notification_dispatch`. Таблица `background_jobs` в ТЗ соответствует внутренним таблицам pg-boss + собственному тонкому слою логирования поверх (для audit).

### Админка
Next.js (App Router) + TypeScript, серверная авторизация администратора (отдельная таблица `admin_users`, не путать с `users`), защищена отдельным паролем/сессией, не имеет отношения к мобильной авторизации.

### AI-провайдеры
Интерфейсы `SpeechToTextProvider`, `StructuredExtractionProvider`, `EmbeddingProvider`, `ModerationProvider` в `packages/ai`. Конкретные реализации подключаются через `packages/config` (имя провайдера и модель — из конфигурации, без релиза). По умолчанию — экономные модели (Haiku/GPT-4o-mini/Gemini Flash уровня) для extraction; правило-based moderation для дешёвых случаев, AI-moderation — только для пограничных. Локальная разработка — `MockAIProvider` для всех четырёх интерфейсов (детерминированные фикстуры, без сетевых вызовов).

## 3. Деплой (по вашей схеме)

Ваша схема верна для backend-части, уточняю роли и добавляю недостающий кусок — мобильную сборку, которая по определению не «хостится»:

```
GitHub (монорепозиторий ustal/)
   │  git push → GitHub Actions (CI/CD)
   │    ├── lint / typecheck / unit / integration tests
   │    ├── build Docker images: api, worker, admin
   │    └── docker push → registry
   ▼
Timeweb Cloud — App Platform (Cloud Apps)
   ├── api      (деплой из Dockerfile, REST, порт наружу через HTTPS)
   ├── worker   (деплой из Dockerfile, без внешнего порта, читает pg-boss очередь)
   └── admin    (деплой из Dockerfile, отдельный поддомен, доступ только для сотрудников)
   │  запросы к БД по приватной сети / DSN из секретов App Platform
   ▼
PostgreSQL — self-hosted на облачном сервере Timeweb Cloud, с расширением
   pgvector, установленным вручную (apt-пакет postgresql-16-pgvector, как и
   в этой сессии при локальной проверке). Managed PostgreSQL от Timeweb Cloud
   рассматривается как альтернатива, если у него подтвердится поддержка
   произвольных расширений (pgvector в списке разрешённых официально не
   значится на момент написания — проверить в поддержке перед переключением).
   + Object Storage (S3-совместимое хранилище Timeweb Cloud, для фото заказов
     и, опционально, аудиозаписей) — в исходной схеме отсутствовало, добавляю:
     без него негде хранить order_media и voice-вложения.

Мобильное приложение — ОТДЕЛЬНЫЙ канал, не хостинг:
   GitHub → EAS Build (Expo Application Services)
     ├── Android: собирает .aab/.apk, может публиковать в Play Console
     └── iOS: собирает .ipa, требует Apple Developer аккаунт (см. открытые вопросы)
   Push-уведомления идут через Expo Push API → APNs (iOS) / FCM (Android),
   backend лишь вызывает Expo Push API (provider abstraction в packages/ai или
   отдельный packages/notifications).
```

Timeweb Cloud App Platform умеет собирать и автодеплоить приложение прямо из
Dockerfile или docker-compose.yml по git push (в т.ч. по подключённому GitHub-
репозиторию, без отдельного шага docker push в сторонний registry) — это
упрощает пайплайн CI/CD относительно первоначальной трёхступенчатой схемы:
можно оставить lint/typecheck/test в GitHub Actions как гейт для PR, а сборку
образов и раскладку по контейнерам доверить самой App Platform.

## 4. Границы MVP (география, деньги, роли)
Только RU, только выбор города (без гео/карт/PostGIS), цены в копейках/RUB, время в UTC + отображение по таймзоне города, единый тип аккаунта, без комиссии — ranking и matching не содержат платёжных полей.

## 5. Найденные противоречия и неточности ТЗ — с минимальными решениями

Ниже — то, что нашлось при вычитке. По каждому пункту: в чём неточность и какое минимальное решение принято (без остановки всего проекта), как и требует сам документ («При противоречии останови соответствующую часть и опиши минимальное решение»).

1. **Нумерация разделов сбита начиная с раздела 13–14.** Разделы 14, 16, 18, 21, 28, 34, 37 встречаются в тексте дважды с разным содержанием (похоже на артефакт копипаста при финальной сборке промпта). Решение: содержание читалось семантически по заголовкам, а не по номерам; в документации проекта разделы пронумерованы заново по смыслу.
2. **ORM не выбран** («Prisma или Drizzle»). Решение: Drizzle — обоснование в разделе 2.
3. **Библиотека очереди на Postgres не названа.** Решение: pg-boss — обоснование в разделе 2.
4. **Object Storage отсутствует в списке сущностей и в вашей схеме деплоя**, при этом `order_media` и голосовые вложения требуют файлового хранилища. Решение: добавлено явно (Yandex Object Storage либо Supabase Storage — см. раздел 3).
5. **WhatsApp-контакт пользователя не описан как отдельное поле данных**, хотя раздел 18 говорит «написать вотсап (если указал в профиле для связи)». Решение: добавляется `user_profiles.whatsapp_phone nullable` (может отличаться от основного номера).
6. **Скрытие числа выбранных исполнителей — требует уточнения объёма.** Буквально нельзя одновременно (а) дать заказчику список выбранных исполнителей для отметки «выполнено/не выполнено» по каждому и (б) полностью скрыть от него сам факт количества — он неизбежно видит список, значит и количество. Решение: правило трактуется как «не показывать число выбранных исполнителей **кандидатам/исполнителям** в ленте, в карточке заказа и в статусе своего отклика» — именно от них скрывается конкуренция. Заказчику в приватном экране «Выбранные исполнители» список показывается естественным образом (это его рабочий инструмент), но нигде не выводится агрегированная метка вида «Выбрано: 3».
7. **Регулируемые задачи и верификация.** В MVP нет OTP и нет проверки документов — то есть по определению ни один пользователь не может быть «подтверждённым» (raздел 24: «До появления полноценной проверки документов такие заказы направляются на ручную модерацию либо не публикуются автоматически»). Явное следствие, которое ТЗ не проговаривает прямо: в MVP регулируемые заказы **всегда** идут в `manual_review` и никогда не становятся `probable`/`new_opportunity` ни для кого — это не баг, а корректное поведение при отсутствии верификации. Зафиксировано как поведение по умолчанию.
8. **`contact_unlock` не имеет лимита** («Не устанавливай лимит… в MVP»), при этом весь остальной документ последовательно защищается от злоупотреблений (rate limiting на AI-правки, идемпотентность). Решение: не вводим лимит по продуктовой логике (как требует ТЗ), но добавляем **техническую** anti-abuse защиту (rate limit на создание contact_unlock, например не более N в час на пользователя), которая не видна пользователю как ограничение продукта и не требует изменений при появлении будущей монетизации.
9. **iOS push и iOS-сборка зависят от одного и того же внешнего фактора** — Apple Developer аккаунта. ТЗ уже требует не имитировать подписанную сборку без реальных credentials (раздел 34) — то же ограничение автоматически распространяется и на боевые APNs push-уведомления. Зафиксировано как единая открытая зависимость, не две разных.
10. **Найдено при реализации Фазы 2 (AI-профиль):** решение «добавить Object Storage» из п.4 фиксировало инфраструктуру, но исходная модель данных (data-model.md) не содержала ни таблицы учёта загруженных файлов, ни хранилища для эмбеддинга профиля, ни места для `Idempotency-Key`, который тот же документ требует от `POST /profile/inputs`/`POST /orders`. Три минимальных добавления, сделанные в БД без остановки фазы:
    - `media` — таблица учёта фото/аудио (владелец, тип, ключ во внешнем хранилище, mime, размер); `order_media.media_id` и `profile_source_inputs.audio_media_id` ссылались в никуда без неё. Доступ к самому файлу — через новый `packages/storage` (тот же паттерн provider-абстракции, что и `packages/ai`): `local` — диск процесса `api`, для разработки; `s3` — Timeweb Cloud Object Storage, заготовка на боевые credentials (как `openAiProviders` в Фазе 1).
    - `idempotency_keys` — общая таблица (user_id + endpoint + key уникальны), переиспользуемая любым endpoint'ом с идемпотентностью, а не отдельная логика на каждый.
    - `profile_embeddings` — таблица 1:1 с версией `capability_profiles`, по образцу уже существовавшей `order_embeddings`: без неё semantic similarity (matching.md §13.2) не могла бы работать для профиля, только для заказа.

11. **Найдено при реализации Фазы 3 (Заказы):** три небольших уточнения, каждое — минимальное расширение уже существующего дизайна, а не новая сущность:
    - `orders.source_text` стал nullable — для голосового заказа текста ещё нет в момент INSERT (транскрипция приходит асинхронно от worker'а), тот же паттерн, что и `profile_source_inputs.transcript` в Фазе 2. Голосовой заказ хранит вложение как `order_media` с `media.kind='audio'` (`position=-1`), без отдельной колонки `audio_media_id` на `orders` — переиспользует то, что уже есть.
    - Машина состояний заказа (`packages/domain/order.ts`) расширена: `processing`/`moderation_hold` теперь допускают переход в `cancelled`. Без этого автор, чей заказ завис на ручной модерации или ещё обрабатывается AI, не мог бы отменить его сам — блокирующий UX-тупик, который ТЗ не подразумевало.
    - `POST /orders/{id}/publish`: api.md формулировал условие как «`moderation_status = allow`» буквально; трактуется как «`allow` или `allow_with_warning`» — иначе у статуса `allow_with_warning` не было бы смысла (предупреждение показывается автору, а не блокирует публикацию, в отличие от `manual_review`/`reject`).

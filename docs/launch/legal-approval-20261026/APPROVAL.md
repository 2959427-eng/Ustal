# Решения владельца перед публикацией

Пять соседних Markdown/HTML-страниц сформированы из существующего API-renderer, а не из отдельной реализации. Это тексты на утверждение; HTML является просмотром текста, рабочую форму удаления добавляет существующий API route. `review-input.json` содержит `approved: false`, это НЕ production bundle. Маркеры незавершённого согласования дополнительно отклоняются валидатором даже при ошибочном изменении флага на true.

Нужны только следующие ответы:

1. Подтверждённое правовое основание AI-обработки при текущем OFF. Если такого основания нет, этим обновлением ссылок обработка не легализуется; отдельное решение о consent enforcement остаётся вне этого изменения.
2. Договорное юридическое лицо OpenAI и фактические настройки/условия нашего аккаунта; страны размещения и обработки конкретных PostgreSQL, S3, backups, relay и OpenAI. Стандартные условия не подменяют подтверждение конкретных ресурсов.
3. Сроки либо критерии хранения персональных остатков истории, AI-кэшей, журналов, жалоб и consent-записей; период ротации backups и порядок исключения уже удалённых сведений после restore. Автоудаление аккаунтов/истории и новые TTL не предлагаются.

ФИО оператора, бесплатность, 0%, 18+, первый рынок Россия и support@ustal.site уже включены. Неподтверждённая страна проживания оператора исключена; не добавлены адрес/ИНН/паспорт. Дата вступления в силу определяется утверждённым днём публикации. Нельзя утверждать выполненными незавершённые требования РКН.

После ответов заменить только отмеченные фрагменты реальными сведениями, заново сформировать эти же пять страниц, получить одобрение их точного текста/версии и лишь затем подготовить approved publication bundle вне Git.

## Единый rollout после отдельных разрешений

1. Согласовать точный commit и выполнить отдельно разрешённые commit/push только release/ustal-1.0.0; сверить remote SHA/tree. Сейчас ничего не сохранено в GitHub.
2. Сверить production SHA/config; сохранить текущие image IDs/Caddy/config и media-cleanup outbox. Создать свежий pg_dump, checksum и восстановить в изолированной тестовой БД; проверить схему, migration0029 и контрольные показатели. Не подключать к ней API/worker и не отправлять данные в AI.
3. Применить проверенный API image, Caddyfile и read-only publication bundle через docker-compose.legal.yml в одном согласованном обновлении. Validate Caddy до reload; проверить файл/validator до запуска API. Не менять worker, AI Consent, matching, БД и мобильные сборки. При несовпадении фактической схемы — STOP, без автоматических миграций.
4. Проверить 5 API URL200; 4 информационных URL ustal.site200; site/delete-account302 → API/delete-account200; CSS/JS200 с правильным MIME, www redirect, TLS и отсутствие циклов. Проверить неизменность health/admin и запрет site/auth и site/me.
5. На iPhone build2 и Android build4 открыть все5 ссылок и AI-screen privacy, проверить чтение/возврат/отсутствие404 и пустых экранов. Android устройство ещё требуется; native PASS не заявлен.
6. При технической неудаче вернуть сохранённый Caddy и совместимый API image/config, сохранив БД/volumes/outbox. Restore БД не является штатным откатом: сначала согласовать обработку удалений после backup, чтобы не восстановить удалённые персональные сведения. Приоритет — forward-fix.
